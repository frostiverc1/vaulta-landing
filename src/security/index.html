The short version

Five statements a security reviewer can test. Each is expanded below with its mechanism and its limits.

One process touches the meeting, and it has no network.

Audio, transcripts and the memo model run in a short-lived, sandboxed session process. Its sandbox profile has no network entitlement, so the OS refuses its sockets. Verified

Verbatim data lives in an encrypted, pinned vault.

Per-record AES-256-GCM, with the key and data held in mlocked memory. It is zeroed and read back to confirm at approval, review timeout, sleep, quit, loss of the control link, or a termination signal. Approval, review timeout, sleep, termination signals and loss of the control link were each run live with the built app. Power-off and a normal quit were not. Verified

The process then exits.

When a process exits, the kernel zeroes its pages before reuse. That sweeps up copies the vault cannot reach. Verified

Every session ends with a signed receipt.

A non-exportable Secure Enclave P-256 key signs it. The backend refuses software-signed receipts by default. Verified

We list what is not done.

Notarization, a production model-signing key, single sign-on from the Mac app and several live-testing gaps are open. They are in Known limits, not buried.

Architecture: two processes, one boundary

The client is split so that the only code that ever sees verbatim audio or text cannot reach the network, and is destroyed when its job is done.

Long-lived · menu bar app

Control process

  • Starts and kills session processes.
  • Owns all network traffic, policy, enrollment and receipt signing.
  • Stores approved memos (encrypted, one file each).
  • Never receives audio or verbatim text. It receives the approved, sanitized memo, a shred report and model hashes.
  • Not sandboxed. See Known limits.
Network: yes, HTTPS to the control plane
Framed JSON over inherited pipes 4 MB frame cap, version and sequence checked
One per meeting · sandboxed

Session process

  • Capture, voice detection, speech recognition, memo model, numeric check, and the Review window.
  • Holds the vault. Verbatim text never leaves this process.
  • Sandbox entitlements: app-sandbox and device.audio-input. Nothing else.
  • Exits about 1.5 s after reporting the shred. Shreds and exits if the control process disappears.
Network: none. Sockets refused (EPERM)

Defence in depth on egress

  • OS sandbox. The session process has no network entitlement. We observed a sandboxed session launched by the control process get EPERM on connect, while the same code unsandboxed reached the internet. Verified
  • Socket watchdog. An independent check polls the session's descriptor table every 500 ms while the vault holds data and records any IPv4 or IPv6 socket (loopback included, deliberately strict). It samples, so it sees sockets, not traffic: a socket opened and closed between two samples is stopped by the sandbox, not seen by the watchdog. The sandbox is the control; the watchdog is the second witness. Run live on 14 November inside a process with the production sandbox entitlements: it ignored a local-IPC socket, and it flagged a TCP socket the process opened even though the sandbox refused that socket’s connection (EPERM). The documented blind spot also reproduced: a socket opened and closed between two samples was not seen. Verified
  • Build-time boundary. A test fails the build if session-side source uses a network API or depends on the networking module. It cannot inspect third-party dependencies; see Supply chain. Unit-tested

What “shred” does and does not cover

This is the question opposing counsel and your auditors will ask, so we answer it first. The vault’s guarantees are narrow and tested. Copies made elsewhere in the process are handled by process exit.

Copies that exist outside the vault

  • Audio in flight. CoreAudio buffers, the resampler output and a small frame accumulator live in process memory for milliseconds before the vault seals them. Freed heap is not zeroed.
  • Decrypted reads. CryptoKit decrypts into ordinary memory, so each decrypted record exists there until reused.
  • Model working memory. Speech-model tensors, the memo model’s prompt and cache, and every string made from transcript text.
  • System audio services. coreaudiod and the audio HAL hold buffers outside our process and outside our control.
  • Swap and hibernation. Unpinned copies can be paged out. macOS encrypts swap by default, which limits exposure but is not “never written”. mlock does not exclude pages from a hibernation image, which is why a sleep hook shreds. A forced sleep (pmset sleepnow) shredded and verified in a live run. Lid-close and a full hibernation image have not been tested, so we do not yet claim the hook always finishes before the image is written.
How the process boundary closes most of this

The first three copies live in the session process. When it exits, the kernel zeroes its pages before reuse, including copies we cannot see or enumerate. That is why the session is a separate, killed process rather than a promise to scrub every buffer.

The claim we make

Raw audio and verbatim transcripts are held only in encrypted, RAM-pinned buffers. Those buffers and their key are zeroed and verified when the memo is approved, when the review timer expires, or when the Mac goes to sleep. The process that handled the meeting is then terminated.

The claim we do not make

“No trace of the conversation remains anywhere.” Hibernation timing is unmeasured and system audio services are outside our process, so we do not assert it, and our receipts do not either.

The attestation receipt

After every session the control process builds a receipt, signs it with a non-exportable Secure Enclave P-256 key, and uploads it. The backend verifies the signature before counting the session.

  "slm_model_hash": "37e644…",
  "internet_sockets_observed": 0,

  "human_attorney_reviewed": true,
  "shred_cause": "approved",
  "session_process_exited": true,
  "signer": "secure_enclave"
}

How it is signed and checked

  • Signature. ECDSA P-256 over deterministic bytes: sorted keys, no whitespace, ISO-8601 UTC seconds. Formatting or key order cannot change a verdict. The receipt carries a key ID, the first 16 hex characters of the SHA-256 of the public key.
  • “Clean” has a precise meaning. No internet socket observed, vault verified zero, and the OS confirmed the session process exited. A session that crashed before reporting a shred gets an honest receipt that is never clean.
  • Backend policy. Software-signed receipts, which are development only, are refused by default. Verified end to end against the real backend: valid upload, duplicate upload, tampered body (403), software key (403), unknown key (401), and a receipt for another Mac (quarantined). Signature verified independently in Python. Verified
What the receipt does not say

It does not report bytes. macOS exposes no per-process byte counter without private API, so we record whether an internet socket ever existed rather than claim a byte count we did not measure. memset_zero_verified means the vault was verified zero, not that no copy exists anywhere. human_attorney_reviewed records an explicit approval, not the quality of the review.

It does not prove which build signed it. The signature shows that this Mac’s device key signed the receipt. That key is not yet bound to the app’s code identity, so another process running as the same user on that Mac could ask the Secure Enclave to sign. The key is non-exportable and cannot leave the Mac. We tested this by having a differently built app, and one with a different bundle identifier, load and use the same key.

What we found, and what we did about it

WhisperKit and swift-transformers both link Hugging Face download code, and the dependency graph cannot be trimmed. We treat that as a finding, not a footnote. Mitigations, in order: model loading is told not to download, points at explicit local folders, and refuses to start if a required file is missing (tested); the session sandbox has no network entitlement, so an unintended call fails; and a boundary test keeps our own session-side code free of network APIs. One full session on the real control path recorded zero internet sockets. A second full run, of the release build of the session process with all of these libraries linked and the production sandbox entitlements, on the demo call (speech, voice detection, memo model, review, shred, signed receipt) also recorded zero. In the same sandbox, a deliberate connection attempt failed with EPERM. The watchdog samples, so only the sandbox stops a socket opened and closed between samples. That is two runs on one Mac with demo audio, not a broad set of runs.

How models reach the Mac

  • Signed manifest. Downloads are checked against an Ed25519-signed manifest using pinned public keys, with SHA-256 verified before a file becomes visible at its final path. The manifest sequence number is persisted, so an old manifest cannot be replayed. Run live on 14 November: the real updater code fetched a manifest signed by the release tool from a real HTTP server. A valid manifest installed and its file hash matched; a file with one flipped bit was refused and never appeared; replaying an older valid manifest was refused; a manifest signed by an unpinned key and one edited after signing were refused. The live run used stand-in files, a plain-HTTP server on this Mac with a test-only switch, and called the updater directly, not through the app menu. There is still no production signing key. Verified
  • No download at all. Models can be pre-staged by MDM, or installed from an offline kit that carries a SHA-256 list of every file.
  • Production signing key. None has been issued yet, so none is built into the client. Open
  • Third-party conversions. The Silero Core ML and Phi MLX builds come from third-party repositories. We intend to reproduce both conversions from the upstream models before release, so the build does not depend on those repositories staying unchanged. Open
  • Pinned hashes under re-verification. On 14 November we re-hashed the installed models. The speech weights, the large-v3-turbo tokenizer and the Phi-3.5 weights matched our records exactly. Our recorded tree hashes for Silero VAD and Whisper base.en could not be reproduced, so the bill of materials now records the values observed on the installed copies and says so. We have not yet compared those copies with a fresh download of the upstream commits. Open
  • Receipt hash coverage. The model hashes in receipts cover one large weight file per model. A per-file manifest is still to do. Open

Endpoint footprint

What a deployment looks like to your endpoint and network teams.

  • Hardware and OS. Apple silicon, macOS 14.2 or later. Intel Macs are not supported. FileVault is expected on.
  • Permissions. Microphone and system-audio capture, requested once. No virtual audio driver, no meeting bot joining the call, and no screen-recording permission.
  • Network. HTTPS to the control plane you configure. Enrollment links are accepted over HTTPS only and ask the user to confirm the server first. A model host only if you do not pre-stage.
  • Preflight. A built-in check prints pass or fail for OS, hardware, Secure Enclave, models and control plane. It never touches audio.

Deleting the keys makes every stored memo permanently unreadable. That is by design, and it is your offboarding lever. A key file that is present but cannot be used is treated differently: the next meeting does not start, the person sees a plain message, and Vaulta does not silently create a replacement, because a new key would change the device’s identity and orphan stored memos. Control plane: who can change what, and the record of it

The control plane holds org policy, device public keys, signed receipts and the audit log. These are the controls around it.

  • Leavers lose access automatically. Connect Okta or Entra over SCIM 2.0. When your identity provider deactivates or deletes someone, every Mac enrolled under their email is revoked in the same transaction. Their unused enrollment links stop working, and they cannot enroll again until they are reactivated. Unit-tested
  • Revocation reaches shared workspaces. A revoked Mac is refused on its next request and removed from every Deal Room workspace. Those workspaces are flagged for re-keying, so it cannot read later glossary versions. Unit-tested
  • Every admin action is on record. Admin and SCIM changes, failed admin logins and every export are logged in the same transaction as the change. A change is never saved without its entry. Each admin gets their own key, so entries name a person, not a shared account. In a running console, sign-in, a password change and account and organization changes each appeared as an entry naming the person and address, and the chain showed as verified. That run was a local demo on 14 November. Verified
  • The record shows tampering. Each entry carries the hash of the one before it, and the whole chain is re-checked every time the log is read. An edited, deleted or truncated entry is reported with where the chain broke. Concurrent admins still produce one unbroken chain. Unit-tested
  • Audit exports you can check. JSON with a content digest, CSV that is safe to open in a spreadsheet, or PDF. The PDF carries a printed Ed25519 signature anyone can check offline, and can also carry a PAdES signature, so PDF readers show a signature panel and flag any change to the file. Every export also lists the model-weight hashes each session reported and a count of each shred cause, and the signed body includes a plain-language section on what the figures do and do not prove, so a limit cannot be removed without breaking the signature. The admin console can preview the same content on screen. Unit-tested
  • Built for production. The full test suite and every database migration pass on PostgreSQL 16. Failed-credential limits are kept in the database, so they hold across servers. Forwarded client addresses are believed only from proxies you list. The server can refuse plain HTTP, sends HSTS, and can require verified TLS to its database. Unit-tested

Limits of these controls are listed under Known limits. The deployment guide in the review pack covers PostgreSQL, TLS, proxies, admin keys and the PDF certificate.

Known limits and open items

We would rather you read these here than discover them in a pilot.

Limits of the design

Design
The control process is not sandboxed.

By design it never receives audio or verbatim text, but it is long-lived and holds the network connection and the memo store.

Design
Other processes reading our memory is out of scope for now.

Defending against it needs hardened runtime and library validation, which need a Developer ID. Debugger attach is not blocked in development builds; deny-attach is for release builds.

Design
The receipt key is not bound to the app.

A receipt proves that this Mac’s Secure Enclave key signed it, not that an unmodified {{NAME}} build did. Binding the key to the app needs a stable signing identity and is a separate decision. Tested on one Mac with differently built apps.

Design
Approval does not prove careful review.

The click is recorded in the receipt. It is a product control, not a technical one.

Not done or not yet verified

Open
Signing and notarization.

Current builds are ad-hoc signed. A Mac that only runs Developer ID software will refuse them until that is done.

Open
Single sign-on.

The control plane accepts OpenID Connect ID tokens from Okta and Entra. The Mac app does not yet run that sign-in, so devices enroll with a one-time link. SAML-only identity providers are not supported.

Open
Live meeting capture.

Zoom, Teams and Meet capture has had one live test. Run a dry run before relying on it. Remote participants appear as one speaker.

Open
Screen-share cloak.

The Review window opts out of screen sharing at the window level. That is tested on a real window, but not yet against Zoom or QuickTime capture.

Open
Key hand-off across app updates.

Tested on one Mac (macOS 27.2): a Secure Enclave key created by one ad-hoc-signed build was loaded and used by a different build, so enrollment should survive an update. Not tested with a Developer ID certificate, on other macOS versions, or on a clean Mac.

Open
Microphone permission after an update.

With ad-hoc signing, macOS treats each rebuilt app as new and asks for the microphone again; we saw the prompt return after a rebuild. With a stable self-signed certificate, an updated build kept its permission in our test. Not yet tested: the first-launch experience for such a build, or pre-approval through MDM.

Open
Updates.

The app has no updater today. Updates are installed by your administrator through MDM or the offline kit. A notify-only design (a signed release manifest, no silent install, never during a meeting) is proposed, and its open decisions include who holds the release key.

Open
Certifications and third-party assessment.

None are claimed on this page.

Control plane

Open
Identity providers, live.

SCIM is tested with Okta- and Entra-shaped requests, not yet against a live tenant. It syncs users, not groups.

Design
Revocation cannot reach into the Mac.

A revoked Mac loses all server access, but memos already stored on it stay readable by that Mac until its keys are deleted.

Design
The audit chain shows tampering; it does not prevent it.

Someone with full write access to the database could rebuild the whole chain. Export the log regularly and keep its latest hash somewhere they cannot reach.

Open
PDF signer trust.

The PAdES signature is validated with pyHanko, not yet opened in Acrobat. With a self-signed certificate, readers show it as valid once they trust that certificate. A green check by default needs an Adobe-trusted certificate, which we have not bought.

Open
Continuous PostgreSQL testing.

The suite passes on PostgreSQL 16 locally. A CI job that runs it on every change is still to do.

Design
Only failed credentials are rate-limited.

Successful traffic is not throttled by the server. Set a request limit at your proxy as well.
